# Spec — ELN 日期输入改用日历选择器

> Status: ready-for-agent
> 来源（已综合，未做新访谈）：`docs/agents/issue-tracker.md`、`docs/agents/triage-labels.md`、本会话 E2E 验收报告（`.scratch` 外，`F:/elndev/work/shots/e2e_eln_vue3/`）、既有 ADR-0041（重复实现债）、用户本轮口头裁决四项。
> 领域词汇：ELN 项目 / ELN Project、筛选面板 / FilterPanel、行操作弹窗 / RowActionModal、资源中心 / Res Center、预定 / Booking、归档日期 / archived on、日期字面量 / YMD 字符串（`'YYYY-MM-DD'`）。

## Problem Statement

ELN（eln_ui）前端共有 **17 处日期输入**仍用浏览器原生 `<input type="date">`，散落在 6 个组件里。用户在这17 个位置要录入或修改日期时，只能：

1. **逐字符键入 `2026-10-11`** —— 原生控件在多数桌面浏览器里只显示分段数字框（`年/月/日`），需要精确按位输入，输错一位不会有任何即时反馈；
2. **依赖浏览器本地化顺序** —— 不同系统的日期段顺序、日期格式（`2026/10/11`、`10/11/2026`、`2026-10-11`）不一致，中文/美式/ISO 混用时需要用户自己判断哪个是月哪个是日；
3. **完全无法「看」到月份全貌** —— 想确认「11 月中旬」要离开当前页面去翻日历；对比两个区间是否重叠、找上一个空闲日，都要靠心算。

项目里其实**已经有成熟的日历选择器**：`@vuepic/vue-datepicker@^7.4.1` 在 `package.json` 中，宿主原生页面（`shared/date_time_picker.vue`）已在用它。但ELN 侧从未接入，于是出现同一仓库内两套日期录入体验割裂：原生页有日历，ELN 页只有数字框。

## Solution

在 eln_ui 新架构下建一个**薄封装日期组件** `DateField`，内部直接使用 `@vuepic/vue-datepicker`，对外契约收敛为**日期字面量字符串**（`'YYYY-MM-DD'`，空值为 `''`），从而：

- 17 处调用方的 `v-model` **一行不改**（现状绑定的就是字符串）；
- 消费侧（`buildListQuery()` 直接塞进 `URLSearchParams`、`weekdayOf()` 周几计算、资源台账导出参数、后端 `start_date` / `due_date` 字段）**零改动**；
- 视觉沿用 ELN 自己的设计 token（与 `field-input` / `rc-date` / `bf-bare` 等既有输入样式一致），不把宿主的原生 SciNote 外观带进 ELN；
- 替换按「先新架构、后旧渲染器」分两批落地，每批独立可验。

区间筛选（资源中心的 4 处「从 ~ 至」）**保持两个独立选择器的形态不变**，只在「起始 > 截止」时给出可见警告 —— 不引入 range 模式的数组状态，避免把两个 `ref` 改成数组带来的回归面。

31. 作为一个 ELN 用户，我想日期作为 `YYYY-MM-DD` **原样发送**，以便后端 `Lists::ProjectsService` 的日期比较口径不被破坏。
32. 作为一个 ELN 用户，我想行操作弹窗里点选的日期**保存进 `start_date` / `due_date`**，以便刷新后仍在。
33. 作为一个 ELN 用户，我想资源中心台账/消耗的区间参数**照旧进导出请求**，以便导出的 CSV 反映我筛的区间。
34. 作为一个 ELN 系统维护者，我想 ELN 的日期组件与宿主的原生日期组件**互不干扰**，以便改 ELN 不影响 `/projects` 等原生页。
35. 作为一个 ELN 系统维护者，我想日期转换**只用本地时区的成对函数**，以便不出现时区偏移导致的「差一天」。
36. 作为一个 ELN 系统维护者，我想 17 处调用方**不需要改数据形状**，以便这次重构不波及后端契约。
37. 作为一个 ELN 系统维护者，我想旧 AG Grid 渲染器里的 2 处**与新架构 15 处行为一致**，以便两个列表版本不会给出不同体验。
38. 作为一个 ELN 系统维护者，我想这个改动**不引入新的 npm 依赖**，以便构建时间与镜像体积不增加。

## Implementation Decisions

- **新增一个组件，不新增一个依赖**：`@vuepic/vue-datepicker@^7.4.1` 已在 `package.json`，ELN 只是第一次 import它。构建时间、镜像体积、`Gemfile.lock`/`package-lock` 全部不动。

- **不复用宿主的 `shared/date_time_picker.vue`**（用户已裁决）。理由是**契约冲突**：宿主封装的 `v-model` 收 `Date` 对象、通过 `change` 事件吐字符串、且 `:range` 会切成数组；而 ELN 全链路（`buildListQuery()` 直塞 `URLSearchParams`、`weekdayOf()`、后端 `start_date`/`due_date`）吃的是**字符串**。硬复用要么在 15 处各加一层适配（等于把封装重写一遍，还散在 15 个地方），要么把 ELN 的数据边界改成 `Date`（污染面更大，且要动后端契约）。且宿主视觉与 ELN 自成体系的设计 token 不搭。

- **组件契约（这是全部调用方看到的唯一接口）**：
  - `v-model`：**日期字面量字符串** `'YYYY-MM-DD'`，空 = `''`。与今天原生 `<input type="date">` 的 `v-model` 值**完全一致**，所以 17 处调用方的 data 层一行不改。
  - props：`placeholder`、`disabled`、`clearable`（默认 `true`）、`size`（用于对齐既有 `rc-date` / `bf-bare` 等不同高度）、`invalid`（区间反了时的视觉态）、`dataE2e`。
  - emits：`change`（值同 `v-model`，供需要副作用的场景）。
  - 单日期模式，**不支持 range**（用户已裁决：区间保持两个独立选择器）。

- **字符串转换必须复用既有的本地时区成对函数**，这是最容易被写错的一处：ELN 已有的 `ymd(date)` 用 `getFullYear()/getMonth()/getDate()` 产出字符串，`parseYMD(str)` 用 `new Date(y, m-1, d)` 产出**本地时区午夜**的 `Date`。两者同源同口径，所以转换零偏移。组件内部**禁止**使用 `toISOString().slice(0,10)`（那是 UTC，东八区会把日期减一天）。

- **`v-model` 的初始值允许是 `''`、`null`、`undefined` 或 `Date` 对象**：现状 17 处的初值不统一（多数是 `''`，`BookingForm` 走 `ymd(TODAY)`，旧渲染器走 `.toString().slice(0,10)`）。组件对非字符串输入做防御式归一，**不因为初值形态不同而抛错或显示空白**。

- **弹层定位与裁剪**（这是原生 `<input type="date">` 换成浮层后**新引入**的问题，不是迁移才有的）：ELN 的筛选面板、行操作弹窗、资源中心筛选条都有 `overflow` / `transform` 上下文，浮层若不做处理会被裁掉。组件必须把弹层 teleport 到 `body` 并给足 z-index，使其盖过 AG Grid 弹窗（`row_action_modal` 在 AG Grid 单元格内）与 ELN 自己的 overlay 背板。

- **配置取值对齐既有 ELN 习惯**：周日为一周起点、`auto-apply`（选中即生效、弹层自动关闭）、关闭滚轮翻月、固定 6 行月历、不显示「今天」快捷标记。理由：这些与宿主 `date_time_picker` 的既有行为一致，用户在原生页已形成肌肉记忆。

- **区间反了 = 警告而非阻断**：资源中心的 4 处成对筛选，在「起始 > 截止」时给输入框加 `invalid` 视觉态并给一段说明文案，**但不清空、不阻止查询、不阻止导出**。理由：筛选条件反了通常来自误点，用户需要自己决定是改起始还是改截止；硬阻断会把「改一个值」变成「清空两个值重填」。

- **落地分两批**：
  1. 新架构 5 个组件 15 处（筛选面板 6、新建项目 2、行操作 2、资源中心 4、预定 1）；
  2. 旧 AG Grid 渲染器 2 处。
  两批之间可各自编译验收；第二批完成后两个列表版本的日期体验才真正一致。

- **不改后端、不改 payload、不改 service**：日期字面量口径不变，`Lists::ProjectsService` / `ProjectsService#filter_project_records` / `elm_ui_project_list` 的筛选参数名与格式一律不动。

## 测试决策

**好测试的标准**：只测**外部可见行为**——用户点了日历之后，输入框显示什么、列表变了什么、请求参数发的是什么。不断言组件内部的 ref 名字、computed 名、VueDatePicker 的实例字段（那些是实现细节，重构就该能变）。

**项目现状决定了接缝**：本仓库**零前端测试框架**（`package.json` 无 `vitest`/`jest`，`test/` 下只有 `mailers`，`test/system/` 为 0 个文件）。因此不为这次改动新建测试基础设施 —— 接缝是**上一轮刚跑通 6/6 的那个 Playwright 验收脚本**（ELN Vue3 端到端验收），扩展它。

**要验的行为清单**（对应用户故事）：

| 场景 | 断言 |
|---|---|
| 筛选面板打开 | 日期字段显示日历图标/占位，不再是分段数字框 |
| 点开日历 | 弹层出现完整月历（6 行），未被弹窗边界裁剪 |
| 点某一天 | 输入框显示 `YYYY-MM-DD`；弹层自动关闭 |
| 手动键入 | 输入框接受键入并归一为 `YYYY-MM-DD` |
| 清空 | 值变`''`，占位提示回来；`resetFilters` 后日期一并空 |
| 区间反了 | 起始 11-10 / 截止 11-01 → 出现警告态；列表仍可刷新（不阻断） |
| 预定日期联动 | 点选新日期 → 相邻「· 周X」后缀同步改变；清空 → 后缀消失（不出现「周undefined」） |
| 筛选真生效 | 设定日期 → 抓网络请求，断言 `filters[start_date_from]=2026-10-11` **原样发出** |
| 行保存 | 行操作弹窗选日期保存 → 刷新后列表行日期列不再是 `—` |
| 资源中心区间 | 设定区间 → 抓请求，断言 `range_from` / `range_to` 参数正确 |
| 旧渲染器批次 | 第二批落地后，旧版列表页的日期行为与新版一致 |
| 无回归 | 全部页面 0 JS 错误、0 失败请求（本轮验收脚本已有的基线断言） |

**测试先例**：本仓库前端无既有单测先例可循，因此**唯一先例就是那个 Playwright 脚本本身**——沿用它已有的会话自签（`tooling/scripts/mksession.rb` 现签 Warden 会话 + `context.addCookies` 注入）、沿用它的 `data-e2e` 选择器约定、沿用它「HTTP 状态 + 挂载 + DOM 长度 + console 错误 + 失败请求」五项基线。

**`data-e2e` 补齐是测试的前置条件**：现状 `ResCenter.vue` 与 `BookingForm.vue` 的 `data-e2e` 数量均为 **0**（筛选面板 9 / 新建项目 3 / 行操作 23 / 旧渲染器 20）。这两个组件的日期字段必须在替换时**同时补 `data-e2e`**，否则无法被脚本定位。补 `data-e2e` 是本次改动的一部分，不是测试的额外负担。

## 范围外

- **宿主 `qa_tools/activity_statistics` 的 2 处原生日期输入**（用户已裁决）。该页是纯 ERB 表单 + Bootstrap `form-control`，**没有 Vue 挂载点**；为一个内部活动统计页引入 Vue 挂载点或第二套日期库，收益不匹配成本。它保持原生形态。
- **宿主原生页面**（`/projects`、实验列表、报告等）已用 `shared/date_time_picker.vue`，本次不动。ELN 组件的引入**不得**改变宿主原生页面的行为。
- **日期时间（datetime）与时间（time）选择器**：`<input type="time">` 不在本次范围（如 `BookingForm` 的时间段行）。ELN 目前没有 datetime 需求；将来若需要，`DateField` 可加 `mode` 扩展，但本次不做。
- **区间选择器（range 模式）**：用户已裁决保持两个独立选择器。`FilterPanel` 的三组「从 / 至」同理。
- **后端侧任何改动**：日期口径、筛选参数名、`start_date` / `due_date` 字段、service 层查询逻辑，一律不动。
- **宿主原生 ERB 页面里其他非日期输入**（select / text / checkbox）不在范围。
- **`qa_tools` 之外的其他内部工具页**同理。

## 补充说明

**这个改动的真实风险不在 UI，在时区。** 全链路今天是 `'YYYY-MM-DD'` 字符串，靠`buildListQuery()` 直塞 `URLSearchParams`、靠 `weekdayOf()` 做 `new Date(s + 'T00:00:00')`。这三处都依赖「字符串就是本地日历日」这个前提。`VueDatePicker` 默认吐 `Date` 对象，若哪一处图省事用 `toISOString().slice(0,10)`，东八区会在每天早上把日期**减一天** —— 而且**静默**：筛选照跑、结果照出，只是边界错了。所以 spec 里把「只用既有的本地时区成对函数、禁用 `toISOString`」写成了硬决策而非建议。

**第二风险是弹层裁剪。** 这是从「浏览器原生控件」换成「JS 浮层」才**新出现**的问题：原生控件由浏览器渲染，不受页面 `overflow`/`transform` 影响；自绘浮层会被裁。ELN 的筛选面板、行操作弹窗、资源中心筛选条恰好都有 `overflow` 或 `transform` 上下文，且旧渲染器那2 处还嵌在 AG Grid 单元格里（AG Grid 自带高层级弹层）。迁移后如果日历被切掉一半，用户会觉得「比原生控件还难用」。teleport 到 `body` 是必需项，不是优化项。

**与既有 ADR-0041 的关系**：ADR-0041 记的是「eln_ui 重复实现了宿主 `RowActionModal`，权限规则漏了三层」这类**业务规则**重复。本次是**第三方 UI 库的薄适配**，里面没有业务规则（权限、状态机、校验都不在日期选择器里），且刻意避开宿主封装只因**契约冲突**而非审美。这与 ADR-0041 记的债不是同一类，不构成对那条 ADR 的推翻。若后续 ELN 要把宿主更多 shared 组件接进来，那时应重新评估「封装 vs 复用」的边界。

**执行提醒**：ELN 前端改动的资产链是固定的 —— 定点 webpack 编译（`ENTRIES=<entry> NODE_ENV=production`，配置走 `_targeted_eln.config.js`）→ Sprockets 预编译 → 重启 web 容器。改的是 `.vue` 而非手写 blob，**不需要动 `assets.precompile` 登记**；但若顺手改了 `index.html.erb` 的 `asset_path`，则必须同步补登记并逐个 `grep` manifest 复核（上一轮 `eln_vue3/eln_project_list.css` 漏登记导致整页 500 的教训）。另外 `ResCenter.vue` 与 `BookingForm.vue` 属不同 webpack entry（资源中心、预定页各自打包），编译时 `ENTRIES` 要一次带上。

## 清单勘误（2026-10-11 ticket 03 执行中追加）

**「17 处」这个数字是错的，真实受影响面是 20 处。**

原清单靠 `grep 'type="date"'` 得出，只数到了**浏览器原生日期控件**。
但 `ProjectDetail.vue` 的编辑弹窗里那 3 个日期（立项时间 / 开始日期 / 截止日期）
根本不是 `type="date"`，而是**纯文本 input**，placeholder 写着 `YYYY-MM-DD` ——
它们比原生控件更糟：既没有日历，也没有格式校验，用户能敲 `2026/3/1` 或
「下周一」直接提交到 `start_date` / `due_date`。

用户报的正是这个：「日期弹窗在 eln_project_detail 中 / 点日期框无弹窗」。

### 为什么会漏

清单的检索口径选错了。**按控件类型检索，只能找到已经用对控件的地方。**
真正的口径应该是「按语义检索」：凡是绑定到日期语义字段
（`form.date` / `form.start` / `form.due` / `*Date` / `*_on`）且让用户自由输入的
输入框，都该纳入不论它用的是什么控件。

### 教训（已写进 spec，供后续同类重构照做）

1. 迁移类重构的影响面清单，**不能从旧实现的形式特征检索**——
   旧实现里「最像问题」的那部分永远只是子集。要从**领域字段**出发反查消费方。
2. 手写 UI 替代原生控件时，先问一句「原生控件是这个领域字段的**唯一**入口吗」。
   答案若是「不，详情页还有一套自绘的」，那自绘那套才是用户真正在点的那个。
3. 「点不出弹窗」这类报障，先确认**被点的那个框是不是本次要改的那个框**。
   本轮前两轮都默认了筛选面板，但用户从头到尾说的是详情页。

### 追加范围

| 位置 | 字段 | 原控件 |
|---|---|---|
| `views/ProjectDetail.vue` | `form.approvedOn` | 纯文本 `pd-input` |
| `views/ProjectDetail.vue` | `form.startDate` | 纯文本 `pd-input` |
| `views/ProjectDetail.vue` | `form.dueDate` | 纯文本 `pd-input` |

这三处属 `eln_project_detail` entry，与 `eln_project_list_v3` 是**两个独立产物**，
都要各自预编译。

## 占位提示的方向性错误（2026-10-11 ticket 04 追加）

**ticket 03 的验收断言写反了，ticket 04 已纠正。**

ticket 03 里有一条断言：

```js
check('纯文本 YYYY-MM-DD 日期框清零', legacy.texty === 0, ...)
```

它把「输入框的 placeholder 里写着 `YYYY-MM-DD`」当作**待清理的坏味道**。
方向完全反了 —— 那正是 `ProjectDetail.vue` 当年**主动加**的格式提示，
是详情页唯一告诉用户「该填什么格式」的东西。

### 后果

ticket 03 把那 3 个纯文本框换成 DateField 时，`placeholder` 只写了
`"开始日期"` / `"截止日期"` 这类**语义**词，**丢掉了格式信息**。
于是用户看到的输入框：既没说格式，也没说能不能打字。

用户在 ticket 04 明确要求：「日期框里提示 `YYYY-MM-DD`，并且提示可以直接输入」。

### 两条提示承担的是**不同**的信息，不能互相替代

| 提示类型 | 回答的问题 | 载体 |
|---|---|---|
| 格式提示 `YYYY-MM-DD` | 「长什么样」 | `placeholder` |
| 可输入提示「可直接输入」 | 「能不能打字」 | `placeholder` |
| 语义（起始/截止） | 「是哪一项」 | 外层 `label` / 分组顺序 / `aria-label` |

原生控件的毛病恰恰是**只有语义、只有数字框，没有格式说明**，
用户必须知道本机浏览器用哪种顺序和分隔符。

### 已落地

- `DateField` 内置默认 `placeholder = 'YYYY-MM-DD · 可直接输入'`，
  调用方漏传也有提示（新增调用方天然带这条信息）；
- 调用方可覆盖（`ProjectDetail` 的「未登记则留白」这类语义更贴切的照旧）；
- 资源中心 4 处显式传入同一文案，保持跨页签一致。

### 教训

**验收断言不能只判断「有没有这个东西」，还要判断「这个方向对不对」。**
清零类断言尤其危险：它对"删错了"和"改对了"一视同仁地报 PASS。
写这类断言时，必须回头确认被清掉的那个东西**当初为什么在那里**。
