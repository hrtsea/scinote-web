# Team Management 实现现状与开发计划（addon 形态）

> 依据：官网 <https://www.scinote.net/product/team-management/> + 代码库现状探查（证据带文件:行号）。
> 方法学：`docs/agents/addon-dev-workflow.md`（Phase 0–6）；遵循 addon 铁律——改动只收敛进 `addons/<name>/`，绝不编辑核心 `app/`。
> 状态：截至 2026-09-01 为**现状评估**，绝大多数能力已在 fork 实现；仅 2 项缺口，其中 1 项为上游计划级（不建议 fork）、1 项为 addon 候选。

---

## 一、结论

**本 fork 已实现 Team Management 页面约 90% 的能力**。团队结构、角色与权限、邀请、@/# 协作、任务分配、Overview/日历、报告、电子签名、时区、审计追踪均已落在核心 `app/` 或既有 addon（`esignatures`）。

真实缺口仅 2 项：
- **W1 团队细分 / 限制访问 ELN 特定部分**：上游计划级（enterprise）特性，OSS fork 无 `parent_team`/`child_team` 数据模型，**不建议在 fork 中以 addon 实现**（属核心架构层）。
- **W2 外部伙伴/客户报告与计费自动化（RESTful API ↔ CRM/ERP、定时账单快照）**：核心 `app/` 零实现（`billing`/`accounting`/`invoice`/`RESTful` 全仓 0 命中），是**唯一可行动的 addon 候选**（`addons/partner_reporting`）。

## 四、缺失清单

### W1 — 团队细分 / 限制访问 ELN 特定部分（上游计划级）
- 现象：页面称「细分团队并仅批准访问 ELN 的某些部分，功能取决于 SciNote 计划」。
- 现状：OSS fork 无团队层级模型（`team.rb` 无 `parent_team_id`/`child_team`），仅项目级可见性。
- 决策：**不建议在 fork 以 addon 实现**——属核心数据模型/权限架构层，需改 `team.rb`/`extends.rb` 本体与 `readable_by_user` 链，违反 addon 铁律且 rebase 冲突极高。列为「向上游/商业版对齐」项，本 fork 不承接。

### W2 — 外部伙伴/客户报告与计费自动化（addon 候选）
- 现象：页面称「经 RESTful API 集成 CRM/ERP，定期或按需生成账单快照，自动化会计」。
- 现状：核心 `app/` 零实现；无对外 API 客户端、无账单/发票模型、无定时快照 job。
- 决策：**可作为 addon `addons/partner_reporting/` 实现**（见下）。范围边界：仅做「把客户项目/交付物进度结构化为可推送的报告 + 定时/按需快照 + 对外 API 端点」，不重写核心报告引擎，复用 `reports_controller` 导出能力。

## 五、里程碑（W2 addon 形态）

> 仅 W2 进入实施；W1 不实施。下列为**待 `/grill` 确认**的候选切片，未落地。

- **M0（Phase 0）**：新增 ADR-011（见第六节）写入 `docs/ARCHITECTURE_DECISIONS.md` 第三节。
- **M1（Phase 3）**：脚手架 `addons/partner_reporting/`（`Scinote::PartnerReporting::Engine`，`isolate_namespace`），复制 `addons/i18n` 骨架；Gemfile 一行 + `config/routes.rb` `mount => '/`。
- **M2（Phase 1/4）— 数据模型**：addon 自有迁移 `partner_billing_snapshots`（客户/项目/周期/状态），经 `Extends` 合并注册，`extends.rb` 本体不改。
- **M3 — 报告聚合服务** `Scinote::PartnerReporting::BillingSnapshotService`：复用 `MyModule.active.readable_by_user(...).joins(experiment: :project)` 链（参照 ADR-008 聚合范式）汇总交付物进度/截止，喂入核心报告导出生成结构化草稿。
- **M4 — 对外 API 端点**：addon 控制器暴露 `GET /partner_reporting/snapshots`；权限 `can_read_partner_reporting?(user, team)` 落 `app/permissions/**/*.rb` 自动发现；API 客户端用 `Net::HTTP`/`Faraday`（仓库已有 `biomolecule_toolkit_client.rb` 范式）。
- **M5 — 定时快照**：addon `app/jobs` 定时（参照 ADR-005 异步作业）生成账单快照，可选推 CRM/ERP。
- **M6（Phase 5/6）**：`rubocop addons/partner_reporting` + `brakeman` + `rspec spec/addons/partner_reporting`；ADR-011 补上游冲突点。

## 六、风险

- **W1**：强行以 addon 实现会突破铁律（需改核心 `team.rb`/`readable_by_user`），rebase 冲突极高 → 已判定不实施。
- **W2**：对外 CRM/ERP 契约未定义（需 grill 明确字段/认证），属绿地但有明确复用锚点（报告导出 + webhook 雏形）。
- 时区：W2 快照时间戳须用 `Time.current.utc`（与核心 `overdue` 作用域一致；`Team` 无时区字段，见 ADR-008 风险）。
- 权限：W2 仅加 `can_read_partner_reporting?` 一个权限，复用团队读权限，少改动面。

## 七、工作量估算（粗）

- W1：不在本 fork 范围（建议上游/商业版）。
- W2：约 1 个中型 addon（M1–M6），预估 1 名工程师 1.5–2.5 周（含 grill + TDD + rubocop/brakeman 全绿）；主要不确定在对外 API 契约（M4）。

## 八、拟新增 ADR-011（团队管理现状评估 + W2 addon 候选）

> 待 `/grill` 确认后正式落盘到 `docs/ARCHITECTURE_DECISIONS.md` 第三节。

**ADR-011：Team Management 现状评估——核心已实现，仅外部计费报告为 addon 候选**
- 依据：官网 Team Management 页 6 大能力 + 代码探查。团队/角色/权限/邀请/@# 协作/任务分配/报告/电子签名/时区/审计 **已在 fork 实现**（证据见第二节表）。
- 决策：
  1. **不重建**核心 Team Management（违反 addon 铁律且收益为零）。
  2. **W1（团队细分）判为上游计划级**，本 fork 不承接（需核心 `team.rb` 层级 + `readable_by_user` 改造）。
  3. **W2（外部伙伴计费/报告 REST API 自动化）** 以独立引擎 `addons/partner_reporting/`（`Scinote::PartnerReporting::Engine`，`isolate_namespace`）承载，**绝不改核心 `app/`**；复用 `reports` 导出 + `webhooks` 雏形 + `Extends`/`app/permissions` 自动发现；聚合复用 ADR-008 的 `readable_by_user.joins(experiment: :project)` 范式。
- 影响/风险：W2 对外 CRM/ERP 契约未定，须 grill 明确；其余覆盖点仅 addon 内，rebase 冲突低。
- 关联：`docs/agents/addon-dev-workflow.md`、`docs/team-management/README.md`（官网特性总结）、ADR-003/ADR-005/ADR-007/ADR-008。
