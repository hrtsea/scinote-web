## 二、已核实技术接缝（addon 如何挂接）

- **A — Widget 注册（核心插入点，已用 reference 分析确认）**：`config/initializers/extends.rb:215` 定义 `DEFAULT_DASHBOARD_CONFIGURATION`（**Array**，含 `partial/visible/size/position`）；全仓引用搜索仅 **2 处**——定义(:215) 与唯一读取方 `app/views/dashboards/show.html.erb:10`（`render partial: widget[:partial]`），**fan-in = 1**，hook 点单一且安全。`Extends` 类头部注释明确写「Should not be freezed, as modules might append to this」——**向 `Extends` 常量追加是设计内的扩展机制**。注意：`addon-dev-workflow.md` 示例用的 `.merge!` 是 **Hash 枚举**写法，对 **Array** 无效；addon 须用 `Extends::DEFAULT_DASHBOARD_CONFIGURATION.concat([...])` / `<<`；且仅当 `Scinote::ProjectInsights.enabled?`（读 `ENV['PROJECT_INSIGHTS_ENABLED']`）为真时注册，**不修改 `extends.rb` 本体**（注释警告多 addon 枚举顺序有依赖，故追加到末尾、不预置 `position`）。
  - *Phase 1 复核补充*：现有 3 个 addon（ai_protocols / esignatures / i18n）**均无 `Extends` 常量追加的可用代码先例**（esignatures 仅用 `app/decorators` 注入签名按钮，见其 `engine.rb` 的 `config.to_prepare` 加载 `app/decorators/**/*_decorator*.rb`）。故 P1 必须以冒烟测试断言「追加生效 + partial 被核心视图解析」，作为该 hook 的首个落地验证；并加**去重守卫**（仅当该 `partial` 尚未在数组中时追加），防重复注册。
  - ⚠️ **本 addon 未采用此 hook**：最终决策以独立 `/insights` 页面交付（见第三节第 3 点），故未向 `DEFAULT_DASHBOARD_CONFIGURATION` 追加任何 widget；该 hook 描述仅作技术接缝记录保留。
- **B — 数据模型（复用，零改动）**：`MyModule` 的 `my_module_status_id` / `due_date` + `overdue` 作用域 / `user_my_modules` / `updated_at` / `.active`（`archivable_model` 的 `where(archived: false)`）全可直接用于聚合；聚合链路复用 `Dashboard::CurrentTasksController#load_tasks` 的 `MyModule.active.readable_by_user(current_user, current_team).joins(experiment: :project).where(projects: {archived: false}, experiments: {archived: false})`（注意 `readable_by_user` 双参）。
- **C — 图表库（复用依赖，新建 addon pack）**：`package.json:63` 已含 `echarts ^6.0.0`、`:94` `vue-echarts ^8.0.0`；`app/javascript/packs/vue/design_system/charts.js` 已写好**与官网一致的饼图 + 堆叠柱图 `option` 配置**（但仅挂在 `#charts` 的独立 Vue demo 入口，未被任何视图引用，且 dashboard 是 erb+Turbolinks，不能直嵌该 Vue app）。addon 在自有 pack `insights_charts.js` 中**复制该 `option` 形状**，在 `turbolinks:load` 遍历 `[data-insights-chart]` 读 JSON 初始化 echarts，**不编辑核心 `charts.js`**。
- **D — 权限（自动发现，但本期不使用）**：addon 的 `app/permissions/**/*.rb` 被 `config/initializers/canaid.rb` 扫描所有 `Scinote*` 引擎自动加入 `permissions_paths`；因 dashboard 已登录门控（current_tasks/calendar 均未单独授权），本期**不新建权限文件**。
- **E — 路由挂载**：主程序 `config/routes.rb` 用 `mount Scinote::ProjectInsights::Engine => '/'` 挂引擎（参考 `addons/i18n` 挂载方式）。addon 内部 `insights#index` 暴露 JSON（模式对齐 `dashboard/current_tasks` 的 AJAX 端点）。
- **F — 视图 partial 解析（引擎视图路径，已确认）**：核心 `render partial: 'dashboards/insights_status'` 会遍历所有引擎的 `app/views` 前缀 `dashboards/` 查找；addon 将 partial 置于 `app/views/dashboards/_insights_status.html.erb` 即可被解析（i18n addon 自行把 `paths['app/views']` 重定向到子目录，本 addon 用默认 `app/views` 即可）。核心 `dashboards/` 下无同名文件，**无命名冲突**；此机制为 Rails Engine 标准行为，P1 冒烟测试一并断言。
- **G — UI 注入备用路径（decorator 先例，本期不采用 Extends 追加）**：esignatures 经 `app/decorators/**/*_decorator*.rb`（`config.to_prepare` 加载）向核心视图注入「签名按钮」——若将来需在不改动 `DEFAULT_DASHBOARD_CONFIGURATION` 的情况下注入动态 UI，可走此路；**本期两者均未采用**——以独立 `/insights` 页面交付，既不向 `DEFAULT_DASHBOARD_CONFIGURATION` 追加 widget，也不引入改动核心视图的 decorator（仅引擎侧 `app/decorators` 覆盖 `LeftMenuBarHelper` / `CurrentTasksController`，属引擎自身视图层）。

## 三、设计决策（经 `/grill` 逼问确认，已回填 ADR-008）

> 以下决策已通过 grill，结论回填 `docs/ARCHITECTURE_DECISIONS.md` ADR-008；原草案的 6 处承重假设错误已校正。

1. **形态 = 独立 addon** `addons/project_insights/`（`Scinote::ProjectInsights::Engine`，`isolate_namespace`），**绝不修改核心 `app/`**。对齐 ADR-006 / ADR-007 已确立范式。
2. **聚合边界 = 团队内可读项目**：所有 widget 数据限定 `current_team` + `readable_by_user(current_user, current_team)`（双参，签名见 `current_tasks_controller.rb:106`），与现有 dashboard 权限一致。
3. **交付形态 = 独立 `/insights` 页面（不挂主 dashboard）**：4 个 widget 以独立页面形态呈现（`insights#index` → 2×2 网格 + 项目选择器）。原计划 P1 设想的 `Extends::DEFAULT_DASHBOARD_CONFIGURATION.concat` dashboard 挂件注册**已废弃**——本 addon 不修改 `DEFAULT_DASHBOARD_CONFIGURATION`，此非偏差而是既定设计。页面渲染复用核心 `charts.js` 的 echarts `option` 与 `current_tasks` 过滤协议。
4. **图表 = 复用 `charts.js` 的 echarts `option` 配置形状 + 新建 addon pack**：dashboard 是 erb+Turbolinks，`charts.js` 为独立 Vue demo 不可直嵌；复制其饼图/堆叠柱图 `option` 到 addon `insights_charts.js`，在 `turbolinks:load` 遍历 `[data-insights-chart]` 读 JSON 初始化 echarts，不改核心 `charts.js`。
5. **下钻 = 复用 `current_tasks` 过滤**：widget 区块链接到 `dashboard_current_tasks_path`（带 `statuses[]`/`mode`/`sort`/`project_id` 预设参数），不新建任务列表页。
6. **灰度门控 = FEATURE_FLAGS（ENV 类）**：不设 `visible: false` 常驻；仅在 `Scinote::ProjectInsights.enabled?`（读 `ENV['PROJECT_INSIGHTS_ENABLED'] == 'true'`）为真时注册 widget，关闭即零渲染零查询，重启 web 生效（对齐 `docs/FEATURE_FLAGS.md` 的全局 ENV 开关约定）。per-team 灰度留作后续扩展。
7. **权限 = 不加新权限**：dashboard 已登录门控（current_tasks/calendar 均未单独授权），本 addon 不新增 `can_view_project_insights?`，少一个改动面。
8. **本 fork 不做无关项**；仅实现 4 个 widget + 下钻。
9. **正确性校正（grill 修正草案错误）**：
   - 截止日期按 **UTC**（`Time.current.utc`，与核心 `overdue` 作用域一致；`Team` 模型无时区字段，原「按团队时区」假设不成立）。
   - 「已完成」用 `completed?` 谓词。**⚠️ 2026-09-01 实证校正**：`state` 列**确实存在**——`app/models/my_module.rb:24` 为 `enum state: Extends::TASKS_STATES`，`config/initializers/extends.rb:17` 定义 `TASKS_STATES = { uncompleted: 0, completed: 1 }`，`completed?` 正是该 enum 自动生成的谓词（全仓搜不到 `def completed?` 即因此，勿据此误判其不存在）。原「`state: completed` 列不存在」的表述错误，但**不影响实现**——仍用 `completed?`。
     - 终态（会把任务置为 completed 的状态）的权威判定范式见核心视图 `app/views/dashboards/_current_tasks.html.erb:37`：`status.my_module_status_consequences.any? { |c| c.type == 'MyModuleStatusConsequences::Completion' }`。
     - 二者因果一致：任务进入上述状态时，`MyModule#exec_status_consequences`（`my_module.rb:584`）会将 `state` 置为 completed，故 `completed?` 与「状态流含 Completion consequence」可等价使用。
   - 截止分桶在聚合服务**现算**（UTC，对齐核心 `overdue` 作用域）；**无 `approaching_due_dates` 作用域**（草案原引 `my_module.rb:135` 为错误引用）。⚠️ **2026-09-04 二次校准**：官方 UI（frame_014 放大复核）为 **5 档** `Overdue / Today / Tomorrow / This week / Next week`——**Overdue 独立成档**（`due_date.to_date < Date.current`），且**无 `More weeks`**，比 Next week 更晚的截止统一归入 **`next_week` 兜底档**。原 4 档 `overdue/due_today/due_this_week/upcoming` 与初版的 `today/.../more_weeks` 均已废弃。

## 四、PRD

**目标（In scope）**
- 以**独立 `/insights` 页面**呈现 Project Insights 的 4 个 widget：状态饼图（含中心总数）、团队负载堆叠柱图（含成员筛选计数）、瓶颈检测（7-14 / 14-N / N+ 天）、截止日期跟踪（Overdue / Today / Tomorrow / This week / Next week）。
- 全部以 `addons/project_insights/` 承载；引擎经 `mount Scinote::ProjectInsights::Engine => '/'` 注册路由（**不**挂主 dashboard，原计划 P1 的 `Extends` 数组追加挂件注册已废弃），复用 `MyModule` 现有数据与 echarts 图表；以 `ENV['PROJECT_INSIGHTS_ENABLED']` 灰度。
- widget 区块点击下钻到现有过滤任务列表。

**非目标（Out of scope，本期）**
- 不改核心 `app/` 任何文件（铁律）；本 addon 以独立 `/insights` 页面交付，**不**经 `Extends` 数组追加 widget。仅在引擎侧 `app/decorators` 用 decorator 覆盖 `LeftMenuBarHelper`（注入左侧菜单入口）与 `CurrentTasksController`（下钻桶位），属引擎自身视图层、未编辑核心 `app/` 文件。
- 不新增独立任务列表页（复用 `current_tasks`）。
- 不新增独立权限文件（复用 dashboard 登录门控）。
- 不实现官方未提及的「物料消耗」「实时推送」等额外 widget。
- 不做 per-team 灰度（仅 deploy 级 ENV 开关）。

**用户故事**
- 作为实验室经理，我想在一屏看到所有并行实验的任务状态分布与谁负载过重。
- 作为项目负责人，我想快速定位 30 天未更新的停滞任务，避免进度悄悄卡住。
- 作为 QA/合规人员，我想一眼看出本周到期/逾期的任务，提前准备审计文档。

- **Issue P2 — 聚合服务** `Scinote::ProjectInsights::AggregatorService`
  - 链路：`MyModule.active.readable_by_user(current_user, current_team).joins(experiment: :project).where(projects: {archived: false}, experiments: {archived: false})`（对齐 `current_tasks_controller.rb:97-147`）。
  - 四个方法（Ruby 侧聚合，避免 N+1；大团队可对 `updated_at`/`due_date`/`my_module_status_id` 建覆盖索引）：
    - `status_overview`：按 `my_module_status_id` group count，回带状态名/色。**⚠️ 2026-09-01 实证校正：状态流不可从 `current_team.my_module_status_flows` 取——`Team` 模型无此关联**，须查询 `MyModuleStatusFlow`（`app/models/my_module_status_flow.rb`）：`belongs_to :team, optional: true`(:7)、`has_many :my_module_statuses`(:6)、`enum visibility: { global: 0, in_team: 1 }`(:4)。即取「当前 team 自有的 `in_team` 流 ∪ `global` 流」，再经其 `my_module_statuses` 取 `name` / `color`；无任务的状态也须回带（计数 0）。
    - `workload`：按 `designated_users` × 状态 group。
    - `bottlenecks`：按 `updated_at` 分 7 / 14 / 30+ 天未更新，**排除 `completed?` 任务**（`completed?` 为 `state` enum 生成的谓词，等价 `state: 'completed'`；SQL 层用 `where.not(state: :completed)`，依据见第三节第 9 点校正）。
    - `due_dates`：四档现算——`overdue`=`is_overdue?`、`due_today`=`due_date.to_date == Date.current`、`due_this_week`=落在当前周、`upcoming`=`due_date` 更晚（UTC，对齐核心 `overdue` 作用域；**无 `approaching_due_dates` 作用域**）。
  - 测试：fixture 任务 → 断言各聚合计数正确（结构契约测试）；覆盖 UTC 边界与 `completed?` 排除。

## 七、风险与注意

1. **状态流可定制**：`my_module_statuses` 由 `my_module_status_flows` 定义，不同团队状态集不同，聚合须动态取当前团队状态流，而非假定固定 5 态。
2. **`charts.js` 不可直嵌**：其为挂在 `#charts` 的独立 Vue demo（写死数据），dashboard 为 erb+Turbolinks；须复制其 echarts `option` 到 addon pack 并在 `turbolinks:load` 初始化，而非复用 Vue app。
3. **（不适用）`Extends` 数组追加**：本 addon 未向 `DEFAULT_DASHBOARD_CONFIGURATION` 追加 widget（独立 `/insights` 页面形态），故该 hook 的合并顺序风险不适用；若未来改为挂主 dashboard 才需考虑 `extends.rb` 注释警告的多 addon 枚举顺序依赖。
4. **性能 / 索引**：大团队聚合（W2/W3）须对 `updated_at` / `due_date` / `my_module_status_id` 建覆盖索引，必要时缓存（dashboard 可容忍分钟级延迟）。
5. **时区**：`Team` 无时区字段；W4「本周 / 今天」按 **UTC**（`Time.current.utc`）计算，与核心 `overdue` 作用域一致，保持全仓统一。
6. **依赖确认**：`package.json` 已含 `echarts ^6.0.0`（:63）与 `vue-echarts ^8.0.0`（:94）；`charts.js` 还 `import 'echarts/core'` 等，依赖齐备，无需补。
7. **灰度实现**：`ENV['PROJECT_INSIGHTS_ENABLED']` 为真才注册 widget；关闭即零渲染零查询，重启 web 生效（对齐 ENV 类开关约定）。
