## 一、结论

**Protocol & SOP Management 是 SciNote 的核心能力，本仓已基本完整实现（约 95%）。** 该页面描述的是既有产品功能，并非本 fork 的绿地需求——绝大多数子能力均已落在核心 `app/`，且受 `app/permissions/protocol.rb` 权限模型与 `Protocol`/`Step` 数据模型支撑。

因此本计划**不做「从零造」式的整体 addon**，仅针对官网描述中**确实缺失 / 仅部分实现**的两点给出可落地的 addon 形态开发计划：

| 缺口 | 严重度 | 是否 addon 可承接 |
|---|---|---|
| **G1 库协议版本变更自动通知**（官网：「库版本变更你会收到通知」）—— 当前仅有手动 `revert`，无自动通知 | 中 | ✅ 可（addon `protocol_version_notifier`） |
| **G2 步骤完成「由谁」** —— 完成人已由 `complete_step` 活动 `owner`(=操作 `current_user`) 记录，UI 未内联展示「完成人」；无独立 `completed_by` 列 | 低 | ✅ 数据已具备，UI 展示可 addon 侧从 `activities` 读取，无需改核心 |
| **G3 SciNote Edit 桌面集成** —— 外部程序；本仓已有「本地程序打开」接入点，属集成增强非缺失 | 信息项 | 现有，无需新建 |

> 与「按需创建协议」相关的 **AI 辅助生成** 属另一独立绿地工作，已在 `0013` + `docs/ai-eln/实现现状与开发计划.md` 规划（`addons/ai_protocols`），本计划不重复展开。

## 三、已核实技术接缝（addon 接入点）

- **A — 协议变更可观测性（核心插入点）**：`Protocol` 已 `include ObservableModel`（`app/models/protocol.rb:17`），模型层具备变更广播能力；发布/更新经 `protocols_controller` 的 `publish_protocol_in_repository` 等动作。addon 可在引擎 `to_prepare` 中订阅 `ActiveSupport::Notifications`（或装饰 `Protocol` 的发布方法），**不碰核心**。
- **B — 关联任务与接收人（复用，不新建）**：`Protocol#all_linked_children`（`protocol.rb:340-344`）→ `linked_my_modules` → 任务 `designated_users`（`my_module.rb:76`）。可直接取「受版本变更影响的用户」集合，无需新增查询基础设施。
- **C — 通知 / 活动基础设施（复用）**：核心已有 `Activities::CreateActivityService`（协议模型内多处使用）+ `app/notifications/`（如 `repository_item_date_notification.rb` 范式）。addon 复用同一套活动/通知原语，不另造。
- **D — 权限（复用，不加新权限）**：协议库读/管理权限已齐备（`app/permissions/protocol.rb`）。通知仅向「能读该协议库且是关联任务 designated user」的人推送，复用既有 `can_read_protocol_in_repository?` 判定，不新增角色。
- **E — 前端提醒（复用）**：任务协议面板可经 `app/decorators` 注入「库已有新版本」提示条，受 `newer_than_parent?` 驱动；亦可仅落活动流（最小实现）。

## 四、设计决策（标注「待 /grill 确认」）

> 以下为分析与初步建议，**进入实施前须经 `/grill` 逼问确认**；结论补进 0017。

1. **范围 = G1（库版本变更通知）+ 可叠加 G2 的 UI 展示**：G2 的完成人数据已存在于 `complete_step` 活动（`owner=current_user`），仅缺内联展示，可由 addon 通过读取该活动实现、**无需改核心**；独立的 `completed_by` 列不推荐（需核心迁移）。G3 为外部集成，不纳入。
2. **通知触发时机**：在 `published_original` 协议被**重新发布新版本**（产生新 `published_version`）时，向 `all_linked_children` 对应任务的 `designated_users` 推送活动 + 通知。
3. **最小 UI**：先在任务协议面板用 decorator 注入「库协议已有新版，可 revert」提示（复用 `newer_than_parent?`）；通知渠道复用既有活动流/通知，不新建邮件类渠道。
4. **铁律守住**：全部改动收敛于 `addons/protocol_version_notifier/`，绝不编辑核心 `app/`；扩展点走 `app/decorators` 与 `ActiveSupport::Notifications` 订阅。

## 五、PRD

**目标（In scope）**
- 当「团队协议库中的某 published_original 协议」发布新版本时，自动通知所有「已链接该协议到任务」的任务负责用户（designated users）。
- 在受影响任务的协议面板上，给出「库已有新版本」提示并提供 revert 入口（revert 本身为核心既有能力）。

**非目标（Out of scope，本期）**
- 不改核心 `app/`（铁律）。
- 不实现 G2（`completed_by` 字段，需核心迁移）。
- 不实现 G3（SciNote Edit 桌面应用，外部程序）。
- 不新建通知渠道（邮件/Slack 等），仅复用活动流/既有通知。

**用户故事**
- 作为团队协议库管理员，我发布协议 v2 后，希望所有在任务中链接了 v1 的成员收到提醒，避免用过期版本执行。
- 作为研究员，我在任务里看到「库协议已有新版本」提示后，可一键 revert 到最新版。

## 九、风险

- **核心钩子不确定性**：`ObservableModel` 是否对外广播 `ActiveSupport::Notifications` 需 grill 时核实；若否，则 P2 改用装饰 `Protocol#publish` 或在 `protocols_controller` 发布动作上 `prepend` 装饰器——二者均不碰核心本体。
- **通知去重 / 频率**：同一协议多次发布需去重，避免刷屏；用「每个 linked_child 仅一条未读活动」约束。
- **revert 语义依赖核心**：提示条的「一键 revert」完全依赖核心 `revert_protocol` 权限与逻辑，addon 不得重写；核心行为变更时需回归。
- **G2/G3 边界**：本次明确不承接，避免 scope 蔓延；若上游未来在核心满足，本 addon 应随之上游收敛。
