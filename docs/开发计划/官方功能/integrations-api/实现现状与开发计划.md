## 〇、结论

官网「Integrations & API」页罗列了 **1 个 RESTful API** + **11 项开箱集成**。经全仓证据核查（见第四节），本 fork 已实现其中 **8 项**（REST API、Protocols.io、Office for the Web、OVE、ChemAxon Marvin、Zebra、FLUICS、Webhooks 自定义集成入口），且多为**核心 `app/` 原生功能**（非 addon）。

**真正缺失的官方集成仅 3 项**：Ganymede、Quartzy、Gilson Connect。三者均为外部云 / 仪器对接，按本仓 addon 铁律，若决定承接应以独立 Rails Engine addon 实现，**绝不修改核心 `app/`**。

> 注：本 fork 已有 4 个 addon（`ai_protocols`、`esignatures`、`i18n`、`project_insights`），均为二次开发模块，与官方集成无关。

## 三、缺失项开发计划（addon 形态，待 `/grill` 确认是否承接）

> 下列三项均为**外部云/仪器对接**，涉及第三方认证、数据契约与隐私，须先经 `/grill` 明确字段、认证与合规边界，再进入脚手架。此处仅给出形态与接缝，不预写代码。

### 3.1 Ganymede（仪器/应用全连接）— 候选 addon `scinote_ganymede`
- **形态**：Rails Engine `Scinote::Ganymede::Engine`，`isolate_namespace`。
- **接缝**：复用 FLUICS 的 `api_client` + `sync_service` 范式对接 Ganymede.bio 数据管道；仪器数据落库到本 fork 既有 `Result`/`Asset` 模型（经 `results_controller` / `assets_controller` API 写入，不碰核心创建逻辑）。
- **风险**：数据契约未定；全实验室自动化平台范围极大，建议先做「单向数据流入」MVP。

### 3.2 Quartzy（云库存同步）— 候选 addon `scinote_quartzy`
- **形态**：Rails Engine `Scinote::Quartzy::Engine`，`isolate_namespace`。
- **接缝**：复用标签打印机设置页（`app/views/label_printers/_fluics_settings.html.erb`）的「云账户连接」UI 范式；同步结果映射到本 fork 既有 Repository / 库存（`app/controllers/api/v1/inventories_controller.rb` 已有库存 API）。
- **风险**：需 org admin 按知识库步骤授权；双向库存再订货超出本期。

### 3.3 Gilson Connect（移液记录）— 候选 addon `scinote_gilson_connect`
- **形态**：Rails Engine `Scinote::GilsonConnect::Engine`，`isolate_namespace`。
- **接缝**：TRACKMAN Connected app 经蓝牙把移液记录上传 → addon 接收并作为 `Result`（或 `Step` 附件）存入 SciNote，复用 `results_controller` API 与 `activities` 记录范式（参照 0017 的活动广播）。
- **风险**：依赖平板端 app 与硬件，本仓无硬件可验证，仅能做数据接收端。

## 五、风险

- **第三方依赖**：Ganymede/Quartzy/Gilson 均需外部账户、API key 与网络可达性；本环境（Windows + 无 GitHub/外网代理）无法联调，仅能离线写客户端与契约测试。
- **数据契约未定**：三项官方集成均超出本 fork 当前数据模型（无 `ganymede`/`quartzy`/`gilson` 表），须经 grill 确认字段映射，避免盲目建表违反 addon 铁律的「复用核心模型」原则。
- **范围膨胀**：Ganymede 是「全实验室自动化平台」，建议砍到 MVP 单向流入；Quartzy/Gilson 同理。
- **rebase 冲突**：若上游未来原生实现这些集成，本 addon 的 `Extends` 合并 / decorator 可能重复触发（参照现有 0013~011 的冲突提示）。
