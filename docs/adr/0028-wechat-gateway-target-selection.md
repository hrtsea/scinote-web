# 0028 — 网关的目标选择：显式 > 上下文 > 引导（含待选两级串联与默认实验持久化）

> 适用范围：`addons/wechat_gateway` 的 `/newexp`、`/newtask` 以及一切需要「确定写到哪里」的入口。
> 依据：2026-09-24 代码核实 + 盘问结论（8 问）。
> 关联：0023（addon 总体）、0025（指令权限校验）、0026（Team 作用域）、0027（无删除指令）。

## Status

Accepted（2026-09-24）。**尚未实现**，落地见 ticket 19–22。Part I（`/newexp` 的项目引导）已于同日先期实现，本文把它的规则提升为通则并推广到 `/newtask`。

## Context

宿主容器层级是硬性的：`Team → Project → Experiment → MyModule`。微信端只有一行文本输入框，没有「先选容器」的表单，所以**任何创建指令都必须先回答「写到哪里」**。

`/newexp` 已按「没预设就问、问完记住、记住后不再问」改造完毕（见 `docs/开发计划/wechat-gateway/项目选择流程设计.md` Part I）。但兄弟指令 `/newtask` 仍停在改造前形态，且更糟：

| | `/newexp`（已改造） | `/newtask`（改造前） |
|---|---|---|
| 缺容器时 | 列候选 → 等编号 → 建 | **回一句用法错误**，用户得先 `/listexp` 抄 ID 再回来（多两次往返） |
| 目标合法性 | `project_available?` 预校验（存在 + 未归档 + 可建实验） | **裸 `Experiment.find(id)`**，无可见性校验（违反 ADR 0025） |
| 目标来源 | 长期默认项目（DB） | 只能行内传 ID |

宿主侧事实：`MyModule` 的创建由 `CreateMyModuleService` 内的 `can_create_experiment_tasks?(@user, experiment)` 把关；项目内实验列表可用 `project.experiments.readable_by_user(user).is_archived(false)`。状态层现状：`wechat_gateway_user_states.pending_action` **只有一个取值** `select_project`。

于是真正的分歧只有一个：**把已经跑通的单级引导，推广成两级（项目 → 实验）时，状态和 wording 要不要重写。**

## Decision

### 1. 目标解析遵循唯一顺序：显式 > 上下文 > 引导

适用于所有创建指令，不各写一套：

1. **显式**：指令行内给出的目标（某指令若支持）。
2. **上下文**（从短到长逐级回落）：**当前实验**（短期索引）→ **默认实验**（长期，本文新增）→ **默认项目**（长期）。
3. **引导**：列候选 → 等编号 → 选完即记住为相应层级的长期值。

### 2. 待选（pending）泛化为「单步 · 可串联」

`pending_action` 取值从 `select_project` 扩到 `select_project | select_experiment`。**两级不是一次存两步队列**，而是第一段消费完就**立刻写入下一个 pending**——同一时刻永远只有一个待选步骤。步骤队列是过度设计：当前最深只有两级。

### 3. 引导级数自适应，不固定

默认项目已记住且有效 → 只列实验（一级）；没有默认项目 → 先列项目（选完顺手记为默认项目），再立刻列该项目的实验（两级串联）。

项目是被长期记住的，绝大多数时候只需要选实验；为「形式对称」多问一次不划算。

### 4. 候选资格对称：列出来的就是能建的

- 项目候选：对用户可读 + `EXPERIMENTS_CREATE` 通过（沿用 Part I）。
- 实验候选：对用户可读 + 未归档 + `can_create_experiment_tasks?` 通过。

列一个用户建不了的东西进去，只会让他选完再撞一次报错。

### 5. 默认实验持久化，但必须消除第二个真值来源

`wechat_gateway_user_states.default_experiment_id`（用户选择，偏离了「仅用短期索引」的原推荐）。

这一列若只是加上，就会造出「当前实验」的两个可以各说各话的来源——术语表 §10 已经为「当前草稿 vs 当前项目」这类混用立过禁令。因此同时规定：

- **短期索引是长期值的缓存**。`SessionDraftStore` 与 `default_experiment_id` 不是两个概念，而是同一个「当前实验」的两种存放寿命；由**唯一解析入口**负责对齐（先读内存，落空则从 DB 恢复并写回）。
- **恢复前必须重新校验**：可见性 + 未归档 + 对应写权限（ADR 0025）。实验比项目更容易过期（会被收尾 / 归档 / 撤权），拿一个过期 ID 直接恢复等于替用户选了一个他早已离开的位置。
- **恢复是一次可见事件**：回复必须带提示行（恢复到哪个实验、`/cancel` 可退出），不许静默接管下一条录入。
- **`/cancel` 同时清短期索引与长期默认实验**。否则「取消」会被下一条消息立刻撤销，用户被困在同一个实验里。

### 6. 空候选必须是明确死胡同，不是自动代建

「该项目下还没有实验」这类分支只给可执行下一步（先 `/newexp` 建、或 `/listproject` 换一个）。**绝不自动创建实验再挂任务**——用户会在 Web 端看到一个名叫 `微信记录-<uid>`、自己完全不认识的容器，而网关按 ADR 0027 又不提供删除。

### 7. `/newtask` 取消行内 ID（破坏性变更）

语法收敛为 `/newtask [任务名] [~截止]`，整串余串当任务名与目标无关。「首位是数字就当 ID」的猜测被否决，原因见下。

### Considered Options

- **保留 `/newtask <实验ID> <任务名>`，首位纯数字即 ID**（否决）：与引导态「纯数字 = 选编号」的规则直接撞车——同一条消息会有两种解释，而选错的代价是任务建到陌生实验里。
- **固定两级引导**（否决）：默认项目已被长期记住的情形下，多问一次只为形式上的一致。
- **待选做成通用步骤队列**（否决）：目前最深两级；队列带来的灵活性与它的存储 / 超时 / 回滚复杂度不成比例。
- **实验只切短期索引、不落库**（原推荐 A，**被否决**，用户选 B）：短期态在多 worker / 进程重启时会丢，用户隔一段时间回来又得重选一遍目标。代价已在 Decision 5 中一并买单；若不愿付这份代价，本决定应被整体逆转——让短期索引单独承担长期职责，与让两个真值来源各自为政是同一件事。
- **自动代建实验以消除空候选**（否决）：见 Decision 6。

## Consequences

- **这是一次破坏性语法变更**：`/newtask <实验ID> …` 不再被当作「指定目标 + 任务名」，整串都当作任务名。必须在 `docs/指令参考.md`、README、`/help` 三处同期标注「⚠️ 历史变更」。
- **本 ADR 建立在 ADR 0025 之上，且必须在其之后实现**。实验候选过滤要读宿主的写权限矩阵（`can_create_experiment_tasks?`，ticket 13），候选可见性要过基座（ticket 11）。在闸门之前先做引导，等于把一份「你可建任务的实验清单」交给一个尚无写权限校验的写入层——**先过闸，再开门**。
- **默认实验会过期**，因此它的每一处消费都要预校验，享受与默认项目同等的待遇；这比项目多一份清理逻辑。
- **`/cancel` 语义被加严**（一并清长期值），与既有文档「只丢本地索引」的说法不一致，需同步修订；被丢弃的实验本身仍然不动（ADR 0027）。
- Part I 的实现（`/newexp` 的项目引导）作为本通则的特例继续有效，其 `SessionDraftStore` / `UserStateStore` 分工不变。
