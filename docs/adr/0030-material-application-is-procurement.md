## 背景

`SQ-2026-7783`（材料类申请：介电磁粉 10kg）审批已到 `completed`，却**既未进入库存、也无任何出入库记录**。

顺着这条 bug 追下去，根因不在实现，而在**领域语言过载**：spec 用同一个词「材料类申请」描述**两种业务**，而这两种业务在**审批通过时的库存方向恰好相反**。

| 业务 | spec 原文 | 审批通过 → 库存 |
| --- | --- | --- |
| **请购（采购入库）** | L60「`RepositoryRow.unit_price`（物料属性，**入库时由请购成本写入**）」／L82「采购/到货验收入库 N 次（无项目）→ **审批通过方可执行**」／L993「**请购单** `proj` 仅作审批依据」／L1179「材料类…仍按既有「**到货验收后再入库** + 任务消耗出库」流程执行」 | **＋ 入库** |
| **领用（从既有库存领出）** | L1100「材料类：**审批通过则出库并扣减库存**」／L1112-1114 `SCN-RES-APPROVE-3`「终审通过，则 系统执行**出库并扣减**对应库存」／L1381「盒内物品…**申请领用**…出库扣减库存沿用 `SCN-RES-APPROVE-3`」 | **− 出库** |

两处原文**直接互斥**：同一个触发点「材料类终审通过」，一处说入库、一处说出库。

而**代码里一条都没实现**——`grep` 全空：addon 中没有任何为材料申请写入或累加库存（建/更新 `RepositoryStockValue`）的代码。已存在的只有「任务消耗 → `RepositoryLedgerRecord` → `ConsumeRecord`」这**一条出库链路**。

雪上加霜的是，2026-10-06 早先的一轮修复**按「领用」语义实现**：要求材料申请单绑定一条**已存在**的库存条目。这在请购语义下方向是反的——`SQ-2026-7783` 的介电磁粉在团队 1 的 14 个库存条目中**根本不存在**：请购语义下它**本该由入库创建**，领用语义下却**无解**（无条目可绑，下拉必然为空）。这也解释了当时为什么会提出「手工新建条目」这种别扭的补救方案——那个提议本身已经承认了语义不对。

## 决定

**D1 · 「材料类申请」＝请购单（采购），不是领用单。**
用户 2026-10-06 拍板：「材料类审批完毕应该进入库存」。申请表达的是**采购需求**，不是从既有库存领出。

**D2 · 入库发生在「到货验收」，不在终审通过。**
用户拍板：终审通过只**解锁**到货验收；实际入库在人工确认到货时执行。理由：审批通过 ≠ 货已到，终审即入库会造成账实不符。与 L82「采购/到货验收入库 N 次（无项目）→ 审批通过方可执行」的字面读法一致（「N 次」= 允许分批到货）。

**D3 · 入库只写数量与单价，不写项目、不计花费。**
沿用 `SCN-RES-COST-4`／L993：入库（建/更新 `RepositoryStockValue`）**不写项目信息、不计入任何项目花费**；请购单的 `proj` 仅作审批依据。`RepositoryRow.unit_price` 在入库时由请购成本写入（L60）。

**D4 · 出库只由任务消耗发生，终审通过不触发任何出库。**
沿用 `REQ-RESOURCE-COST` L57：「出库统一走原生任务消耗（指派项目任务 + `stock_consumption`）」。

**D5 · `SCN-RES-APPROVE-3` 与 `REQ-RES-APPROVE` L1100 的「出库并扣减」措辞是过期的，改写为「入库」。**
这不是新增语义，是把与 L57/L82/L1179 冲突的措辞统一到同一口径。

**D6 · 前端不再要求材料类「绑定已存在的库存条目」。**
改为填名称／数量／单位／单价（＝请购成本）；审批通过后由「到货验收入库」动作创建或累加库存条目。上一轮加的「绑定库存条目」（`RepositoryRow`）下拉**移除**；「关联任务」保留（`SCN-RES-APPLY-1` L1075 本就要求申请单可填「关联任务/实验记录本」）。

**D7 · 申请时必须指定「进入哪个库」（`Repository`），且在申请时选，不在验收时选。**
用户 2026-10-06 指令：「申请的时候就要选择进入哪个库」。
- 申请单材料类新增必填项 **目标库（`Repository`）**，下拉只列**本团队**可读的库；
- 选库的时点定在**申请**而非**验收**：申请人最清楚这批料该进哪个库；到验收时再问一遍，验收人未必知道，且会给「随便点一个」留下空间；
- 入库时在该库内**按申请名称**找已有条目：有则**累加** `RepositoryStockValue`，无则**先建条目**再入库（对应 L993「到货验收**建/更新**库存」的「建/更新」）；
- 目标库跨团队 → 拒绝（沿用 `ResourceApplicationWorkflow` 既有的团队归属校验口径）。
- **与旧语义的区别要写清楚**：上一轮绑的是 `RepositoryRow`（**已存在的具体条目**，领用语义——料已在库里，去领）；本次绑的是 `Repository`（**库**，请购语义——料还没进库，货到了才进）。两者名字像，语义相反。

## 备选方案与为何不采用

| 备选 | 不采用的原因 |
| --- | --- |
| **A. 领用语义：审批通过 → 出库扣减**（`SCN-RES-APPROVE-3` 字面） | 与用户先前明示的「材料类出库要走实验消耗扣减库存，**不是**终审通过自动出库」直接抵触；且解释不了 `SQ-2026-7783` 的介电磁粉在团队内无条目——领用语义下没有可扣减的对象，这个 bug 会永远无解 |
| **B. 两者并存：申请单加「请购/领用」类型，各走各的** | 更贴 spec 全貌（「请购单」与「盒内申请领用」原文都在），但需新增类型字段 + 两套审批后分支 + 两条测试线。**本次范围已由用户收窄为单一请购模型**；见下方「未决」 |
| **C. 终审通过即自动入库**（省掉到货验收） | 审批通过 ≠ 货已到。自动入库会让库存先于实物增加，账实不符，且与 L82「审批通过方可**执行**」的措辞冲突。**取舍：宁可多一道人工确认，不要让账实静默漂移** |
| **D. 保留上一轮的「绑定已存在条目」并叠加入库** | 两套语义叠在一起，申请单会出现「既绑了 A 条目、又要新建 B 条目」的自相矛盾状态 |
| **E. 「进哪个库」推迟到验收时再选** | 验收人未必知道这批料该进哪个库，会把决策推给最没有信息的人；且多一个「随便点一个」的入口。申请人最清楚，时点就定在申请 |

## 代价

- **多一个状态与一道人工环节**：终审通过后单子不会自动变「已完成」，而是停在「待到货验收」，需要项目负责人（沿用终审名单）执行入库动作才收口。停留在中间态的单据必须可见、可催办，否则会积压。
- **`SCN-RES-APPROVE-3` 是被多处引用的场景号**（含 `REQ-LOC-AUDIT` L1381）：改写措辞会连带影响「申请领用」的引用链，须同步核对（见「未决」）。
- **须回退上一轮的前端改动**：材料类的「绑定库存条目」下拉与 `linkedConsumptions` 的绑定前提都要按 D6 重做；已推送的 bundle 需要重新构建与真机验证。

## 未决

**OPEN-PROCURE-1 · `REQ-LOC-AUDIT` 的「申请领用」是否保留为独立流程？**
L1381 要求盒内物品提供「申请领用」入口，且「材料类申请终审通过后的**出库扣减**库存沿用 `SCN-RES-APPROVE-3`」。D5 把 `SCN-RES-APPROVE-3` 改写成「入库」后，这条引用会指向错误语义。
两种可能：①「申请领用」是**另一个入口的另一个业务**（从位置/盒子发起 → 出库扣减），应拥有**自己的场景号**；② 它本就是请购流程的一个入口，出库扣减应改为引用任务消耗链路（D4）。
**本次未决，不在 ADR-0030 范围内**，需用户另行拍板后再改 spec 与实现。
