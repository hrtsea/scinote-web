# 0025 — 微信网关指令对宿主实体一律走「可见性校验 + 写权限闸」，禁止凭 ID 直取

> 适用范围：`addons/wechat_gateway`（命名空间 `Scinote::WechatGateway`）全部按 ID 定位宿主实体的指令。
> 依据：本仓库宿主源码与 addon 代码核实（2026-09-24）。
> 关联：0023（addon 总体）、0024（任务指派语义）。

## Status

Accepted（2026-09-24）。**当前实现违反本 ADR**，需按 issue 补齐。

## Context

addon 以**真实用户身份**直调宿主模型写入（ADR 0023 决策 4），意图是保证 GLP 审计链。但「以谁的身份写」只解决了作者问题，**没有解决「能不能写这条记录」**。

核实结果：addon 的 `scinote_service_writer` 中，以下路径均为**裸查**——拿到 ID 就定位、不经任何可见性判断：

| 写入/读取路径 | 被指令调用 | 校验现状 |
|---|---|---|
| 读实验元信息 | `/setexp`、`#<ID>` | 无 |
| 追加正文 | `/setexp`、`#<ID>`、隐式录入 | 无 |
| **写 `done_at`（收尾）** | `/done` | **无**——宿主 `TimeTrackable#complete!` 本身就是裸 `update!`，不带权限 |
| 列任务 | `/listtask` | 无（连所属实验都不校验） |
| 建任务 | `/newtask` | 部分：宿主 `CreateMyModuleService` 内有 `can_create_experiment_tasks?`，但落到 Rollback 分支返回 `nil`，addon 侧会拿 `nil` 去取 `id` |
| 读/追加/收尾所依赖的实验对象 | 以上全部 | 无 |

后果：任一**已绑定**用户，只要知道一个实验 ID，就能向**任意 Team 的任意实验**追加正文或把它标记为已完成。这不是理论风险——实验 ID 会在 `/list` 结果、群聊转述、邮件里流转。

三条被子路径依赖的解法都已排除：

- 依赖宿主 service 内部校验 → 宿主 sigma service 只在**创建**路径有 `can_create_*?`，**读、追加、收尾**路径没有，且 `complete!` 明确不带权限；
- 依赖 addon 与宿主同进程因此「已经过了应用层」→ 进程内不等于免鉴权，写作者的身份与**写对象的可见性**是两件事；
- 依赖「内网自托管、用户都是同事」→ GLP 场景下**审计要求是记录不可被他人静默修改**，信任模型不构成豁免。

## Decision

**任何按 ID 定位宿主实体（实验、项目、任务）的指令，必须先把该实体放进「对该用户可见」的范围内再取用；任何写动作另需对应的宿主写权限，缺权限时返回友好提示，不得抛裸异常。**

具体而言：

1. **读路径**（`/setexp`、`#<ID>`、`/listtask`、`get_experiment`、`get_project`、`list_mymodules`）经宿主的可读范围取得实体，不可见时按「不存在」处理。
2. **写路径**（`append`、收尾、建任务）在可见性之上加各自的写权限闸：
   - 追加 → 需实验写权限；
   - 收尾 → 需实验管理权限（它写的是 `done_at`，属状态变更，不是随手追加）；
   - 建任务 → 显式校验创建权限，并显式处理「service 返回 `nil`」的情形（不得对 `nil` 取 `id`）。
3. **错误消息不区分「不存在」与「不可见」**，避免把 ID 存在性变成探测通道。
4. **`/admin` 例外**：它是唯一刻意越出个人可见范围的特权查询，已有实例管理员守卫，且**只读**。特权面只此一处，不扩张。

## Consequences

- 权限判断集中在写入层，指令层只做编排——指令可以保持「薄」，新增指令不容易漏掉门禁。
- 用户拿到-403 的机会变多；回复文案必须说清「缺什么权限、去哪儿解决」，否则用户只会反复重试。
- 需要一份「指令 → 所需权限」对照，作为后续新增指令的准入检查表（见 `.scratch/wechat-gateway/issues/13`）。
- **本 ADR 与 ADR 0024 的分工**：0024 决定「派任务 = 指定 Task 成员」的语义；本 ADR 决定「能不能碰到这条 Task」。两者正交。
