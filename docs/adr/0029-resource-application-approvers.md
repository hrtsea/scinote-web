# ADR-0029 资源申请的筛选、可见范围与审批人配置

- 日期：2026-10-05
- 状态：已采纳（grill 结论）
- 相关：`REQ-RES-APPROVER`（spec V1.24 新增）· `REQ-RESOURCE`/`REQ-RES-APPLY`/`REQ-RES-APPROVE`（修订）· PRD V1.24 §7.9.5
- 影响面：`addons/eln_ui`（后端）· `ELN系统-Vue3/src/views/ResCenter.vue`（前端）

## 背景

资源申请列表有三件「规格写了、代码没做」的事，而且是一个问题的三个切面：

1. **筛选是假的**——界面上那行 `筛选：状态 ▾ · 资源类型 ▾ · 申请项目 ▾ · 提交人 ▾` 是静态文本。
2. **可见范围是假的**——服务端把整个团队的申请全量下发，前端按角色藏起来。`REQ-RESOURCE` 说的「项目负责人可管理；组员仅查看本人申请记录」从来没进过数据层。
3. **审批闸门是橡皮图章**——`reviewer_authorized?` = 同团队 + 非本人。原因是 `REQ-RES-APPROVE` 只写了「小组组长初审 → 项目负责人终审」，而原生 SciNote **没有稳定的「小组组长」角色落点**（`待确认 C` / `待确认 G` / OPEN-1）。

## 决定

**D1 · 审批人是显式配置的数据，不是推导出来的角色。**
新增 addon 自有表 `eln_ui_project_approvers`（project_id + stage + user_id），按项目分别配置初审 / 终审名单。理由：绕开「小组组长」这个没有落点的角色，而不是继续给它造一个假的落点。副作用是好的——评审人名单本身就是一份可读的组织档案。

**D2 · 名单即闸门，且 fail-closed。**
未配置某阶段 → 该阶段无人可审批，提示「请先配置该阶段审批人」。宁可卡住，不要放行。

**D3 · 可见范围与审批闸门共用同一个策略服务（`ResourceApprovalPolicy`）。**
可见范围 = 项目负责人 ∪ 任一阶段审批人 ∪ 提交人本人。两件事分两处写必然漂移，这是本次最容易出现的技术债。

**D4 · 可见范围必须在服务端过滤。**
「把前端 JS 关掉，越权数据也不该出现在 payload 里」作为判定句。前端只做展示层筛选，不承担权限裁决。

**D5 · 筛选的发生顺序不可颠倒：可见范围 → 筛选。**
`filterOptions` 的下拉选项也只从可见范围内的记录推导（否则下拉项本身就泄漏存在性）。

**D6 · 「项目负责人」沿用现有唯一口径**，即 `UserAssignment` + `UserRole.find_predefined_owner_role`（与任务关闭、通知publish 已经是同一套）。OPEN-1 的双轨悬案不在本次 reopen。

## 备选方案与为何不采用

| 备选 | 不采用的原因 |
| --- | --- |
| **A. 给模型加 `role` 字段 / 复用 `UserAssignment` 存审批人** | 审批人会跟角色权限混在一起，删一个审批人牵扯 RBAC；且要在几位交错不同的赋值层里递推「谁继承谁」。审批人是「某项目的一时安排」，不是权限包——新表干净得多 |
| **B. 用上述英语 JSON 列存在项目扩展表上** | 查询要捞出来再 Ruby 侧过滤，做不了索引与 JOIN，可见范围过滤会退化成全表扫。而 PK/唯一索引能替我拦住的重复，我不想自己管 |
| **C. 继续 Jenkins 角色硬解（项目成员 ↔ 小组组长）** | 原点就是没有「小组组长」落点，硬解只能继续复制「同团队非本人」。这是橡皮图章的延续 |
| **D. 未配置时回退到「同团队非本人」宽口径** | 与 D2 直接冲突：宽口径一旦留着，就没人会去配名单，这个配置能力会自己废掉。**取舍：宁可卡住（可见且可修），不要静默放行（不可见且不可修）** |
| **E. 可见范围放在前端差不多的心智负担下做** | 等于没做。权限不能依赖客户端 |

## 代价

- fail-closed 会让「配了申请流程但没配人」的项目卡住，处理成本落在项目负责人身上（阻塞文案必须指出找谁配）。这是有意识的成本转移：从「安全静默失效」转到「配置责任人可见地欠着」。
- 多一张表、多一处策略服务：修增加的权限/可见性判定都要过 `ResourceApprovalPolicy`，不许行 PGP 捷径。
